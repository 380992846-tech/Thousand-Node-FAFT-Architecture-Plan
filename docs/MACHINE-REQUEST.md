# 机时申请（一页版）

> 依据与详细论证见 [`ROADMAP.md`](ROADMAP.md) §三之二。这一页是申请正文。

## 要什么

| 项 | 数量 | 用途 |
|---|---|---|
| **A800 GPU** | **0 张** | 共识层不需要 GPU |
| CPU 节点 | **6 台**（最小）／**12–15 台**（推荐） | 真实多机下的 Raft 元数据面实测 |
| 压测端 | 1–3 台（可复用上述节点） | 单进程压测端在 ~9k ops/s 就饱和 |
| GPU（**可选**） | **8 张（1 台 8 卡）** | 采集真实 checkpoint 突发轨迹 |

**单节点规格**：8–16 核 / 32 GB / **NVMe SSD** / **10 GbE**，优先裸机。

**硬性条件**：故障域必须**真的独立**（不同机柜/供电）。
否则"整域故障"不可复现，而这是我们唯一能检验的主张。

## 为什么不要 GPU

论文的落点在**元数据面**：Raft 的 quorum 几何与副本放置。
GPU 不参与共识 —— 这一点在代码注释里就写死了：

> 这里跑的不是千卡集群，是**千分片元数据面**：GPU 不参与共识，
> 真正压到元数据层的是分片数、故障域数与故障的相关性。

申请 A800 不但没用，还会让实验**更难做**：GPU 机器更少、更同质，
很难凑出 5 个真正独立的故障域。

## 为什么必须换机器（三条实测依据）

1. **单机已经到硬上限**。`分片数 × 副本数 ≤ 3000` 是实测出来的上限
   —— 5000 个 Raft 实例连续跑到第 7 次会把整台机器打到失去响应
   （当时物理内存还剩 22.8 GB，不是内存问题，是选举风暴把 16 个核打满）。
   单机不能再堆，只能换机器。
2. **单机结果已被证明不可外推**。同一结构下：400 分片（1200 实例）稳定等于
   算术界；1000 分片（3000 实例）只有 71.6%/90.5%/96.0%，另一次
   34.3%/50.9%/100.0%。原因是 CPU 饱和导致选举活锁。
   **这不是"想要更大规模"，是已有证据说明单机量不出真实可用性。**
3. **缺真实网络与真实磁盘**。目前跨机 RTT 是代码注入的、日志在内存里。

## 拿到之后做什么

| 实验 | 产出 | 消掉哪条局限 |
|---|---|---|
| 同一组 quorum 几何在真实跨机 RTT 下重跑 | "注入 vs 真实"的偏离量 | L1 |
| 多机下重复整域故障矩阵 | 可用比例是否等于算术界 | L3、L12 |
| 真实 NVMe 上的 \|Q2\| 收益 | fsync 与 quorum 等待的重叠程度 | L4 |
| 多机压测端打 16–32 分片 | 吞吐是否终于随分片数上升 | L10 |
| （可选）1 台 8 卡跑真实训练 + checkpoint | 真实的 K、突发宽度、周期 | L5（最弱一环） |

## 规模是怎么定的

- `n=5, D=5` 恰好落在 **5 台机器**上：杀 1 个域后剩 4 台 ≥ `|Q1|=4`，
  正是对照表里 `(4,2)` 那一行。**5 台是这个实验的最小闭包。**
- 推荐档（12–15 台）是为了让**每台承载多个分片** —— 真实部署就是这样，
  而"可用比例与实例数相关"那件事只有在这个形态下才测得到。

## 给资源评审的一句话

> 我们要 6–15 台 NVMe + 10 GbE 的 CPU 节点、分布在 ≥3 个独立故障域，
> 用于真实多机下的 Raft 元数据面实测（整域故障后的可用比例、真实 RTT 下的
> quorum 几何收益、真实 fsync 下的持久化代价）。**共识层不需要 GPU。**
> 另需 1 台 8 卡机器采集真实 checkpoint 突发轨迹，用于标定负载模型。
>
> 依据：单机装置已实测出硬性上限（3000 个 Raft 实例时 CPU 饱和导致选举活锁，
> 可用比例退化为 34%–100% 的区间），因此论文中的规模化结论**只能靠多机获得**。
