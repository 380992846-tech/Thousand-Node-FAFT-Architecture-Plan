# 故障参数实测：要挖哪些数据、怎么统计、怎么喂回求解器

> **这份文档要解决的，是本项目当前最弱的一环。**
>
> `pkg/faft` 的全部可用性结论——包括"按故障域组织 quorum 能把可用性维持在
> 0.99999"这个核心主张——都建立在**假设的**故障模型参数上：
>
> ```go
> faft.CorrelatedFailure{P: 每域独立失效率, Q: 区域事件率, K: 事件命中域数}
> ```
>
> 这三个数决定求解器会选哪套 quorum 几何。而**结论对参数的敏感性，
> 远大于对算法的敏感性**。审稿人只要问一句"你这些参数哪来的"，
> 现在只能回答"估的"。
>
> 真实集群的运维日志里，这三个数**已经存在**，只是没人去算。
> 这份文档 + `cmd/faultfit` 就是那个"去算"的东西。

---

## 1. 需要哪些数

| 参数 | 代码位置 | 语义 | 从哪来 |
|---|---|---|---|
| `P` | `CorrelatedFailure.P` | 每个域**独立**整体失效的概率（每观测窗口） | 域级故障区间 → `faultfit` |
| `Q` | `CorrelatedFailure.Q` | 一次"同时打掉多个域"的事件的发生概率（每窗口） | 同上，由时间重叠扫描得出 |
| `K` | `CorrelatedFailure.K` | 一次这样的事件打掉几个域 | 同上，取峰值并发域数的众数 |
| `Domain.FailProb` | `Topology.Domains[i].FailProb` | 逐域失效率（表达"某些域更不可靠"） | 同上，逐域 P |
| `RegionalEventProb` / `RegionalEventDomains` | `Topology` | 与 Q/K 同义，用于 `SolveWithFailures` 路径 | 同上 |
| `RTTMs` | `Topology.Domains[i].RTTMs` | 域间往返延迟矩阵 | 集群网络探针 / `ping` 矩阵 |
| `Capacity` | `Topology.Domains[i].Capacity` | 每域可容纳副本数上限 | 容量规划（非故障数据） |
| `EgressCostPerMB` | `Topology.Domains[i].EgressCostPerMB` | 出口单价 | 计费清单（非故障数据） |

**只有前五项需要"挖数据"**，后三项是基础设施事实，运维那边问一句就有。

## 2. 数据源清单（按层给，逐层都可能产出"域级故障"）

判据只有一条：**这一层出问题时，整个域的副本是不是一起不可用？**
是，才记一行；不是，它是节点级故障，需要先按域聚合。

### 2.1 GPU 层（对训练集群最重要）

| 数据 | 来源 | 用途 |
|---|---|---|
| Xid 错误码与发生时刻 | `dmesg`、DCGM `DCGM_FI_DEV_XID_ERRORS`、`nvidia-smi -q` | 判断单卡故障；**一个域内 Xid 集中爆发往往先于整域故障** |
| ECC 不可纠正错误 | DCGM `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` | 单卡降级 |
| NVLink 错误计数 | `nvidia-smi nvlink -e`、DCGM NVLink 指标 | 机内互联退化 |
| 掉卡 / 掉驱动 | Xid 79（GPU 掉总线）、Xid 94/95 | 常导致整机不可用 |

### 2.2 节点层

| 数据 | 来源 | 用途 |
|---|---|---|
| 节点 NotReady 区间 | kube-state-metrics `kube_node_status_condition` | 节点级故障区间 |
| 内核 panic / 重启 | `node_exporter` `node_boot_time_seconds` 跳变 | 硬重启 |
| 整机掉电 | BMC / IPMI SEL 日志 | **往往同时打掉整个机架** |

### 2.3 网络层（区域事件的主要来源）

| 数据 | 来源 | 用途 |
|---|---|---|
| IB 端口错误 | `port_rcv_errors`、`symbol_error`、`link_downed`、`port_xmit_discards` | 链路退化 |
| ToR / leaf 交换机事件 | 交换机 syslog、SNMP trap | **整 leaf 失效 = 典型的区域事件** |
| BGP 抖动 / 路由收敛 | 路由器日志 | 跨域连通性 |
| NCCL 超时 | 训练日志 `NCCL timeout` / `Watchdog caught collective operation timeout` | 网络问题的最终表现 |

### 2.4 域层（直接产出"域级故障区间"）

| 数据 | 来源 |
|---|---|
| 可用区 / 机架级不可用 | 云厂商事件 API、内部 oncall 记录、机房巡检 |
| PDU / 供电事件 | BMC SEL、UPS 日志 |
| 计划内维护 | 变更单系统（**必须单独标注**，见 §4.3） |

### 2.5 作业层（ground truth，用来校验上面的判断）

| 数据 | 来源 |
|---|---|
| 训练作业重启记录与原因 | 调度器（Slurm / Volcano / K8s）作业历史 |
| 重启时的故障归因 | 训练框架的故障归因模块 |

> **为什么要有这一层**：前三层给出的是"什么坏了"，这一层给出的是
> "坏了以后训练停了多久"。两者对不上，说明"域级故障"的判据定错了。
> 这是唯一能外部校验判据的东西。

## 3. 输出格式（`cmd/faultfit` 的输入）

CSV，三列带表头：

```csv
start,end,domain
2026-01-01T03:12:00Z,2026-01-01T03:19:30Z,az-a
2026-01-01T07:41:00Z,2026-01-01T07:41:45Z,az-c
2026-01-01T11:02:00Z,,az-b
```

- `start` / `end`：RFC3339。`end` 留空表示延续到数据末尾。
- `domain`：故障域标识。**域的定义必须固定并写进论文** ——
  同一份数据按"可用区"切和按"机架"切，会得出完全不同的 P/Q/K。

## 4. 采集时的四个判据（定错了整个拟合就废了）

### 4.1 「域级故障」怎么算

不能简单用"域内 ≥N 个节点同时挂了"——那会随集群规模漂移。
建议用**影响面判据**：

> 该域内的副本有超过 X%（建议 **50%**）在同一时刻不可用，且持续超过
> T（建议 **1 分钟**，避免瞬时抖动）。X 与 T 都必须写进论文。

备选判据是"该域内的训练作业全部中断"，这个更贴近业务定义，
但要求有作业层数据。

### 4.2 重叠 ≠ 同窗口

区域事件的定义是 **"在某段真实时间里同时有 ≥2 个域下线"**，
不是"两个域在同一个窗口里都故障过"。

后者会把整个观测期摊平：在 60 天的数据上，任何两个域"都故障过"的概率都很高，
于是 Q 会被高估几个数量级。`faultfit` 用的是时间线扫描（sweep line），
不是窗口计数 —— 这一点在代码里有注释。

### 4.3 计划内维护必须单独标出来

滚动升级、机房割接造成的"域不可用"不是故障。混进去会让 P 虚高。
建议在 CSV 里加一列 `kind`（planned / unplanned），或者干脆导出时过滤掉。

### 4.4 观测窗口怎么选

`P` 和 `Q` 都是**"每观测窗口"**的概率，换窗口它们就变。选法：

> **窗口 ≥ 3 × 该域的平均故障恢复时长（MTTR）**

理由：一次持续 D 分钟的故障会跨 1–2 个窗口，逐窗口计数因此系统性偏高
`1 + D/W` 倍。窗口越大于 D，这个膨胀越小。

`faultfit` 会算出平均/中位故障时长并给这个警告。窗口长度**必须和结果一起报**，
否则数字不可比。

## 5. 用 `cmd/faultfit` 拟合

```bash
go run ./cmd/faultfit -in failures.csv -window 6h -physical 20m -out-json faultparams.json
```

输出五块：逐域 P（边际 / 独立）、Q、K 分布、**两两相关性检验**、
以及可直接粘进 Go 的参数块。

### 自检（没有真实数据也能验证工具正确）

```bash
go run ./cmd/faultfit -synthetic -domains 6 -days 365 -window 6h \
    -trueP 0.004 -trueQ 0.02 -trueK 3
```

按已知参数生成合成故障序列再反解，看能不能估回来。

**实测自检结果**（本仓库回归用）：

| 注入真值 P | 真值 Q | 真值 K | 拟合 边际 P | 拟合 **独立 P** | 拟合 Q | 拟合 K |
|---|---|---|---|---|---|---|
| 0.004 | 0.02 | 3 | 0.02284 | 0.00607 | 0.02427 | **3** ✓ |
| 0.0005 | 0.005 | 2 | 0.00296 | 0.00074 | 0.00665 | **2** ✓ |
| 0.01 | 0.05 | 4 | 0.06168 | 0.01367 | 0.04480 | **4** ✓ |
| 0.002 | 0.01 | 5 | 0.01647 | 0.00275 | 0.01098 | **5** ✓ |

- **K 四档全部精确复原。**
- **Q 误差约 ±20%**（窗口重叠的残余）。
- **独立 P 系统性偏高约 1.4–1.5×**，来源是 §4.4 的窗口重叠膨胀
  （`1 + D/W`）。`faultfit` 不自动除这个因子 —— 膨胀因子依赖"故障何时发生"
  的分布假设，把它留在报告里由使用者判断更诚实。

> **关键一步：必须用"独立 P"而不是"边际 P"。**
> `CorrelatedFailure.P` 的语义是**独立**失效率，区域事件已经由 Q/K 表达。
> 而逐窗口直接数出来的是**边际**值。用边际值 = 区域事件算两遍。
> 自检里这一步差了 **5 倍**（0.0200 vs 0.004）—— 这个坑正是自检发现的。

### 5.1 相关性检验：lift 不能单独看

`faultfit` 会为每一对域算 `lift = 实测共同失效占比 ÷ 独立假设预测`。
lift ≫ 1 是区域事件存在的证据 —— **但只在"期望次数"够大时才可解读**。

这条是回归测试逼出来的：真 Q=0 的场景下，365 天、6 个域、P=0.01，
**期望共同失效窗口数只有 0.16 次**；实际撞上 1 次，lift 直接报 **7.7×**。
看起来像强相关，其实全是小样本噪声。

所以 `faultfit` 现在把 `expected_co_failure_windows` 和 lift 一起报，
并在期望次数 < 5 时标注"lift 不可解读"。**论文里报 lift 必须带期望次数。**

> 判据是期望次数，不是 lift 的大小。期望次数 ≥ 5 之后，lift 才是一个
> 有统计意义的量。

## 6. 拿不到数据怎么办（很可能的情况）

**不要编参数然后当成实测报。** 正确做法是把结论改成**敏感性扫描**，
并明确说明参数空间：

1. 对 `P`、`Q`、`K` 各取一个**合理区间**（例如 P ∈ [1e-4, 1e-2]，
   Q ∈ [1e-3, 1e-1]，K ∈ [2, D/2]），在区间上做网格或拉丁超立方扫描。
2. 画出**结论对参数的等值线**：哪些参数区域里"按域组织"占优，哪些区域里
   不占优。**分界线本身就是结论**，而且它不依赖具体参数值。
3. 论文里这样写：

   > 由于无法取得生产集群的故障日志，我们报告结论在故障参数空间上的
   > 敏感性。在 P ∈ […]、Q ∈ […]、K ∈ […] 的范围内，
   > 域感知几何在 XX% 的参数组合上优于均匀几何；分界线位于 […]。
   > 我们同时给出用 `cmd/faultfit` 从真实日志拟合参数的完整方法，
   > 供后续工作使用。

这比"我们假设 P=1e-4"强得多：审稿人要的是**结论的稳健性**，
不是一个漂亮但没根据的数。

## 7. 验收标准

拿到的数据要能过这几关，才值得写进论文：

| 检查 | 标准 |
|---|---|
| 样本量 | 多域事件 **≥ 30 次**（否则 Q 的置信区间约 ±1/√n，n=6 时就是 ±41%） |
| 窗口尺度 | 窗口 ≥ 3 × 中位故障时长 |
| 计划内维护 | 已分离，且论文里说明了分离方式 |
| 域定义 | 固定且写进论文（可用区 vs 机架会给出不同的 P/Q/K） |
| 外部校验 | 与作业层重启记录对得上（§2.5） |
| 相关性 | 两两 lift 明显 > 1（否则区域事件不是主要矛盾，FAFT 的收益点要重新论证） |

最后一条尤其重要：**如果 lift ≈ 1，说明这个集群的相关故障很弱**，
那么 FAFT 的核心卖点就不成立 —— 这个结论要在动手写论文**之前**得到，
而不是被审稿人问出来。

## 8. 与其它部分的关系

- 参数算出来之后 → `pkg/faft` 的 `SolveWithFailures` 直接吃（见 §1 的代码位置）
- 想验证"参数换了以后选出的几何真的更好" → `cmd/raftbench -mode shards`
  （见 [MEASUREMENT.md](MEASUREMENT.md) §5.8：它测的是同一件事的真实 Raft 版本）
- 两者的关系：`pkg/faft` 用解析概率回答"选哪套几何"，
  `raftbench -mode shards` 用真实 Raft 回答"这套几何在整域故障下活下来几个分片"。
  **前者依赖本文档的参数，后者不依赖** —— 所以后者可以作为前者的校验。
