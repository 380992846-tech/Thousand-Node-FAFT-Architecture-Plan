1. **BUG-16（路由层从不转发）** —— 严重在它**不是崩溃、不是报错，而是假装成功**。

### 1.4 另外两条"用自己写的基准打自己脸"的

- **读路径 Barrier**：`BenchmarkGetRaw` 578 ns/op vs `BenchmarkBarrier` 6,672,332 ns/op —— **慢 11500 倍**。

  `b=1, t_fsync=5.4ms → 185 ops/s`，与实测 `BenchmarkSet` 的 ~184 ops/s 吻合。
  修复（readIndex 语义）后实测吞吐 396 → **2014 ops/s**，get p50 39.13 → **4.09 ms**。

- **ephemeral 端口**：这条的价值不在修复本身，而在**它为什么值得记录** ——
  **生产环境用固定端口时症状完全隐藏**。只有测试用 `:0` 才暴露。
  这是"测试配置与生产配置不同，掩盖了一整类缺陷"的典型。

# 第二部分 · 时钟地板（为什么亚毫秒延迟测不出来）

## 2.1 现象与实测数据

本机的 Go **单调时钟是粗粒度跳变**的。这不是代码问题，是运行环境（虚拟化时钟）的属性。
实测（`cmd/raftbench` 启动时自测，写进结果的 `clock_floor_us`）：

| 测量项 | 实测结果 |
|---|---|
| 200 ms 忙等中的**非零时钟跳变**次数 | **142 次** |
| 跳变的最小值 / p50 / p90 / 最大值 | **301.8µs / 992.1µs / 4.05ms / 4.52ms** |
| `time.Sleep(10µs)` 最快返回 | **521µs** |
| `time.Sleep(50µs)` 最快返回 | 440µs |
| `time.Sleep(500µs)` 最快返回 | 532µs |
| `time.Sleep(1ms)` 最快返回 | 1.03ms |
| 同一段 20e6 次忙循环的 10 次测量 | 8.98 – 16.56ms（**±40%**） |

**怎么读这张表**：

- 200ms 里只有 142 次跳变 → **时钟大约每 1.4ms 才走一格**，而不是每纳秒一格。
- `time.Sleep(10µs)` 要 521µs 才返回 → **睡眠的物理下限约 440–520µs**，与请求值无关。
- 同一段忙循环十次差 ±40% → 连 CPU 计时本身都不可靠。

## 2.2 直接后果：**低于约 1ms 的延迟读数全部无效**

最直接的证据是 `raftbench -dump` 的 `raw_latency_ns`：在 in-memory 介质（`-delay 0`）下，
**所有样本都是 0**。这不是 bug，是时钟根本分辨不出来。

具体到本项目的三处影响：

1. **端到端基准**（`cmd/kvbench`）测的是几十毫秒级的延迟 —— **高于地板，可用**。
   这也是为什么"get p50 39.13 → 4.09ms"是可主张的。
2. **共识层微基准**（`cmd/raftbench`）在 `-delay 0` 下的延迟**不可用**，
   只有吞吐可用（跨秒窗口，噪声被平均掉）。
3. **注入延迟 < 1ms 时同样不可用** —— 所以 `raftbench` 的扫描从 1ms 起步，
   且 `latency_usable` 字段会显式标记。

## 2.3 三道防线（怎么绕开它，而不是假装它不存在）

| 防线 | 做法 |
|---|---|
| **量出来** | `probeClockFloor()` 在每次运行开始时自测最小跳变，写进结果的 `clock_floor_us` —— **随结果一起落盘，读者自己判断** |
| **标记** | `latency_usable` / `observed_p50_ms`：判据是"实测 p50 ≥ 3× 时钟地板"。为 false 时 `notes` 里有显式警告 |
| **换指标** | 延迟不可信时，主指标换成**吞吐**（跨秒窗口）；另给 `derived_avg_latency_ms`（Little 定律 `W = L/λ = 并发数 ÷ 吞吐`）—— 它**只用两个聚合量，不受时钟地板影响** |

还有一条容易被忽略的：`client_saturation` = 客户端等待 Apply 的总时长 ÷ (并发 × 窗口)。
**它接近 1 时，吞吐才代表服务端容量**；否则吞吐只是"并发数 ÷ 延迟"，跨配置比较容量不可靠。

## 2.4 讲这段时的一句话

> 这个限制**不是我们能修的** —— 它来自运行环境。
> 能做的是**把它量出来、写进结果、在解读时避开**。
>
> 审稿人问"为什么你 in-memory 的延迟是 0"，答案就是 2.1 那张表。
> 主动讲比被问出来强得多。

# 第三部分 · 确定性复现：真实情况是什么

## 3.1 先纠正："113 个同种子逐位复现的测试"不存在

实际数字（可按下面的命令自己数）：

| 项 | 实际值 |
|---|---|
| 测试函数总数（`^func Test`） | **173** |
| Benchmark 总数 | 11 |
| **与确定性直接相关的测试** | **2 个**，外加 1 个反向对照 |

那 2 个是：

1. **`TestWorkloadDeterministic`**（`pkg/bench/bench_test.go:260`）
   —— "同种子必须产生同序列"，验证**负载生成器**的确定性。
2. **`TestEncodeDeterministic`**（`pkg/raft/node.go` 的回归测试，`node_test.go:83`）
   —— "同输入 ⇒ 同字节"，**200 次编码逐字节比对**。

反向对照 1 个：**`TestWorkloadDifferentSeedsDiffer`** —— 不同种子必须产生不同序列
（否则"同种子同结果"是废话，因为随便什么都同结果）。

## 3.2 那"同种子 ⇒ 同结果"这句话从哪来的

它是 **`cmd/kvbench` 这个驱动的性质**，写在 `ROADMAP.md` 与 `DESIGN.md` 的实现表里：

> `cmd/kvbench` | 一体化实验驱动：**同命令 + 同种子 ⇒ 同结果**

`cmd/kvbench` 确实有 `-seed`（默认 42），并传给 `Workload`。
所以准确的说法是：

> **实验驱动是可复现的：给定同一条命令与同一个种子，负载序列、分片划分、key 访问顺序都相同。**

而不是"有 113 个测试在验证逐位复现"。

## 3.3 关键区分：**"负载序列可复现" ≠ "测量结果逐位可复现"**

这两件事必须分开讲，混起来是硬伤：

| | 可复现吗 | 证据 |
|---|---|---|
| **负载序列**（哪些 key、什么顺序、读写比例） | ✅ 是 | `TestWorkloadDeterministic` |
| **编码字节**（日志条目、快照） | ✅ 是，逐字节 | `TestEncodeDeterministic`（200 次） |
| **测量结果**（吞吐、延迟分位） | ❌ **不是，也做不到** | 同一配置 5 轮内波动可达 **72k–184k ops/s**；忙循环 ±40% |

**为什么测量结果不可能逐位复现**：结果里含时间。而且这台机器的时钟地板与调度抖动
（见第二部分）本身就带来了 ±30–40% 的波动。任何人声称"基准测试逐位可复现"，
只要在同一台机器上连跑两次就会被推翻。

**正确的说法**：

> 实验**驱动**是确定性的（同种子 ⇒ 同负载序列），
> 因此**不同方法之间的比较是公平的**（大家跑的是同一串请求）。
> 但**绝对数字不可跨轮次比较** —— 所以论文里报**区间**与**同轮内的相对关系**，
> 不报单点倍数。这一点在 `MEASUREMENT.md` §5.1 已经写明。

## 3.4 真正做了的"可复现"是什么

比"113 个测试"更实在的三件事：

1. **一键复现脚本**：`scripts/run-raftbench.ps1` 把实验矩阵（A–F 六组）固化下来，
   含全部参数与输出路径。任何人跑同一条命令得到同一组实验。
2. **合成自检**：`cmd/faultfit -synthetic` 按**已知参数**生成故障序列再反解，
   断言能估回来（K 四档全部精确复原）。这是"没有真实数据也能验证工具正确"的手段。
3. **结果带环境元数据**：每个结果 JSON 都带 `clock_floor_us`、`injected_delay_us`、
   `gc_percent`、`max_append_entries`、`client_saturation` —— **读者能自己判断这组数字在什么条件下取得**。
