# 测量方法、证据分级与本机限制

> 这份文档存在的唯一目的：让论文里的每一个数字都能被追问「它是怎么来的」，
> 并且答案是可复现的命令，而不是「我记得跑过」。
>
> 本项目曾经把解析计算写成「本项目实测」。那是错的，而且是很严重的一类错。
> 所以规则定死：**任何数字在写进论文之前，先在这里找到它的行**。

## 1. 四级证据

| 等级 | 含义 | 可以主张什么 | 不可以主张什么 |
|---|---|---|---|
| **MEASURED** | 真实系统跑出来的 | 本机、本配置下的绝对性能 | 其他硬件/网络/规模下的绝对性能 |
| **ANALYSIS** | 组合概率、闭式成本模型、约束求解 | 成本界、结构性质、可行性 | **任何性能声明** |
| **SIMULATED** | 离散事件模拟，且经实测校准 | 趋势 | 绝对值；校准未过时还须标注偏离规模点 |
| **DERIVED** | 本项目自行推导（非引用、非实测） | 作为推导结论 | 当作发现（若文献已有，须引用） |

代码里的对应物是 `pkg/faft/evidence.go` 的 `Evidence` 枚举与
`EvidenceManifest()`。清单可以直接跑出来核对：

```bash
go run ./cmd/faftbench evidence
```

**判据（写论文时逐条过）**：

1. 这个数字来自哪一级？
2. 这一级允许我写"我们测得"吗？不允许就改成"我们分析得出"。
3. 有没有把 ANALYSIS 的数放进性能表？—— 这是最容易犯的错。

## 2. 三套测量装置，各管一段

| 装置 | 产出 | 介质 | 能回答 | 不能回答 |
|---|---|---|---|---|
| `cmd/kvbench` | `results/{smoke-2x3,readheavy-after,writeheavy}.json` | 单机、BoltDB fsync、进程内 HTTP | 端到端读写延迟/吞吐；优化前后的相对改善 | 真实多机；大规模 |
| `cmd/raftbench` | `results/raftbench-*.json` | 单进程多 goroutine、in-memory 日志与传输 | **共识层**：quorum 几何对提交延迟/吞吐/消息数的影响 | 端到端吞吐；真实网络 |
| `pkg/sim` + `cmd/simbench` | `results/` 之外，随命令输出 | 离散事件 | 大规模下的趋势 | 绝对值（且校准未通过，见 §5） |

三者**不可互相替代**。特别是：

- `raftbench` 的数字**不是**「这个系统能跑多少 QPS」。
  它测的是共识协议本身，把路由、编解码、存储、fsync 全部剥掉了。
  它存在的意义是：把 `|Q1|`/`|Q2|` 这两个整数与吞吐/延迟的因果关系
  **单独隔离出来**，这在端到端基准里做不到（那些开销会把信号淹掉）。
- `pkg/faft` 的数字**不是**延迟也不是吞吐。它是概率与计数。

## 3. raftbench 的设计属性（为什么它的对照可信）

### 3.1 基线与实验组共用同一份代码

`third_party/flexiraft` 是 `hashicorp/raft@v1.6.1` 的改造版。在
`DataQuorumSize=0` 且 `ElectionQuorumSize=0` 时：

```
quorumSize()                  -> voters/2 + 1     （= 上游）
dataQuorumSize()              -> voters/2 + 1     （= 上游）
commitment.recalculate() 的 q  -> 回退到多数        （= 上游）
```

也就是与上游**逐行等价**。于是：

| 组 | DataQuorumSize | ElectionQuorumSize |
|---|---|---|
| majority（基线） | 0（= 多数） | 0（= 多数） |
| FlexiRaft | k+1 | 由 \|Q1\|+\|Q2\|>N 定 |

实现差异这个混淆变量被**彻底排除** —— 两组跑的是同一个二进制、
同一段提交逻辑，只差两个整数。

> 如果这里换成「上游 hashicorp/raft vs 某个独立实现的 FlexiRaft」，
> 任何差异都会被质疑「是不是实现质量问题」。这是本设计最重要的属性。

### 3.2 安全性条件在入口拦截

Flexible Paxos 要求 `|Q1| + |Q2| > N`（Howard et al., OPODIS 2016 §4.2）。
违反它**不会报错**，只会静默地丢已提交的日志。fork 内部只知道自己那一个
quorum，无法自检，所以 `buildCluster` 在建立集群前直接拒绝该组合。

### 3.3 一致性检查比的是状态指纹，不只是条数

跑完比每个节点的 `(applied 条数, lastIndex, hash)`。
`hash` 是 FSM 把每条命令的序号与 index 一起混进的状态指纹，
它能抓住「两个节点在同一 index 应用了不同命令」——只比条数抓不住。

这个检查在开发中**真的抓到过东西**：早先的 harness 复用 payload 缓冲区，
而 `InmemStore` 与 `InmemTransport` 传的都是引用，导致已提交的日志内容
被后续迭代改写。症状正是「条数与 lastIndex 完全一致、hash 不一致」。

### 3.4 in-memory 介质量不出 quorum 效应，所以要注入延迟

`InmemTransport` 的 RPC 是进程内 channel 传递，一次 AppendEntries 往返
只有几微秒。在这个介质上，「少等一个副本」几乎看不出差别 ——
不是机制不成立，而是**被测量的介质里没有等待**。

`cmd/raftbench/net.go` 在发送侧给每条 RPC 注入单程延迟：

- 延迟服从对数正态，**中位数**为配置值（用中位数而非均值，
  参数含义才不随 sigma 漂移）；
- pipeline 路径的语义是 `enqueue_i = max(t_i + d_i, enqueue_{i-1})`，
  即**按序交付但允许多个在途**（TCP 的模型），并用
  `maxInflightPerPeer` 做 BDP 上界与背压；
- 这是**注入**的延迟，不是实测网络延迟。所有结果都带
  `injected_delay_us` / `injected_jitter_sigma` 字段，论文里必须一起写。

> 这一条曾经写错过：早先的实现是「先等前一个 enqueue，再 sleep(d)」，
> 于是 `enqueue_i = enqueue_{i-1} + d_i` —— 延迟变成**累加**，每个 follower
> 的吞吐被钉死在 1/d，实测 p50 从 2ms 爆到 169ms，连心跳都排不上队，
> leader 反复因 lease 失效退位而不断重新选举。
> 症状是「延迟大得不像话 + term 一直涨」，很容易被误读成协议问题。

## 4. 本机限制（必须随结果一起读）

### 4.1 时钟地板 ≈ 300µs，且跳变可达 4.5ms

本机 Go 单调时钟是**粗粒度跳变**的。实测（`cmd/raftbench` 启动时自测，
写进结果的 `clock_floor_us`）：

| 测量 | 结果 |
|---|---|
| 200ms 忙等中的非零时钟跳变 | 142 次 |
| 跳变最小值 / p50 / p90 / 最大值 | 301.8µs / 992.1µs / 4.05ms / 4.52ms |
| `time.Sleep(10µs)` 最快返回 | 521µs |
| `time.Sleep(50µs)` 最快返回 | 440µs |
| `time.Sleep(500µs)` 最快返回 | 532µs |
| `time.Sleep(1ms)` 最快返回 | 1.03ms |
| 同一段 20e6 次忙循环的 10 次测量 | 8.98 – 16.56ms（±40%） |

**后果**：

1. **任何低于约 1ms 的延迟测量都会读成 0。**
   在 in-memory 介质（`-delay 0`）下逐次测延迟是无意义的 ——
   `raw_latency_ns` 全是 0 就是证据，不是 bug。
2. 结果里的 `latency_usable` 字段标记了这一轮延迟是否可信：
   判据是「注入延迟 ≥ 3× 时钟地板」。为 false 时，`notes` 里有一条
   显式警告。
3. 延迟不可信时，**主指标换成吞吐**：吞吐用跨秒窗口计算，
   时钟噪声会被平均掉。另外提供 `derived_avg_latency_ms`
   （Little 定律 `W = L/λ = 并发数 ÷ 吞吐`），它只用两个聚合量，
   同样不受时钟地板影响。
4. `client_saturation` = 客户端等待 Apply 的总时长 ÷ (并发 × 窗口)。
   **它接近 1 时吞吐才代表服务端容量**；否则吞吐只是「并发数 ÷ 延迟」，
   跨配置比较容量是不可靠的。

> 这条限制不是本项目能修的 —— 它来自运行环境（虚拟化时钟）。
> 能做的是**把它量出来、写进结果、在解读时避开**。
> 审稿人问「为什么 in-memory 的延迟是 0」，答案在这张表里。

### 4.2 单机、单进程

所有节点跑在同一进程里，共享同一个 Go 调度器与同一个物理 CPU。
所以：

- n 不能太大。n=9 以上测到的更多是**调度器**而不是协议。
- 没有真实的网络分区、没有跨机 RTT、没有共享交换机故障。
- 注入延迟是**模拟**网络，不是真实网络。

### 4.3 没有 `-race`

本机无 C 编译器（`-race` 需要 cgo）。所有并发代码的验证只有
逻辑推理 + 功能性并发测试。详见 [`ROADMAP.md`](ROADMAP.md) §三。

## 5. 实测结果（MEASURED 级）

以下全部来自 `results/raftbench-*.json`，由
`scripts/run-raftbench.ps1` 一键复现。
统一配置：n=5、payload 64B、512 并发、每轮 2s、重复 3 轮取中位数、
每条 RPC 注入单程延迟（对数正态，中位数如表中所示，sigma=0.6）。

### 5.1 收益侧：quorum 几何 × 网络 RTT

吞吐（ops/s，3 轮中位数，方括号是 3 轮的极值区间）：

| 注入单程延迟 | \|Q1\|=3 \|Q2\|=3（多数） | \|Q1\|=4 \|Q2\|=2 | \|Q1\|=5 \|Q2\|=1 |
|---|---|---|---|
| **0（纯内存介质）** | 173,895 `[126k–206k]` | 204,282 `[181k–210k]` | 148,717 `[126k–205k]` |
| **1 ms** | 161,737 `[121k–162k]` | 165,130 `[155k–187k]` | 156,507 `[147k–223k]` |
| **2 ms** | 92,810 `[86k–94k]` | 99,376 `[86k–117k]` | 116,719 `[116k–159k]` |
| **5 ms** | 38,506 `[38k–39k]` | 45,956 `[45k–49k]` | **154,437 `[91k–169k]`** |

p50 提交延迟（ms，3 轮最小值）：

| 注入单程延迟 | \|Q1\|=3 \|Q2\|=3 | \|Q1\|=4 \|Q2\|=2 | \|Q1\|=5 \|Q2\|=1 |
|---|---|---|---|
| 0 | 2.172 | 2.172 | 2.215 |
| 1 ms | 2.866 | 2.446 | 2.172 |
| 2 ms | 5.191 | 4.093 | 2.596 |
| 5 ms | 12.909 | 9.979 | **2.701** |

**读法（以及不能读成什么）**：

1. **延迟为 0 时三组没有区别**（126k–210k 全都落在同一噪声带里）。
   这是关键的**对照条件**：介质里没有等待，`|Q2|` 变小就没有收益。
   收益确实来自"不等副本"，不是实现差异或批次效应。
2. **1 ms 时也看不出区别**（121k–223k，三组区间重叠）。
   本机轮间波动 ±30%，1 ms 的效应被淹在噪声里 —— 这一档应当报成
   **"效应落在噪声内"**，不要从中挑一个方向写结论。
3. **多数 quorum 的吞吐随 RTT 近似反比下滑**：
   174k → 162k → 93k → 39k（0 → 1 → 2 → 5ms）。
4. **`|Q2|=1` 基本不随 RTT 变化**（149k / 157k / 117k / 154k）——
   提交路径上**完全不等 follower**，网络被移出了热路径。
5. 差距随 RTT 拉大：5 ms 时 `|Q2|=1` 是多数 quorum 的 **4.0 倍**；
   2 ms 时 1.26 倍。

> ⚠️ **不要把 4.0 倍写成"5.3 倍"**：上一轮跑到过 5.3 倍，这一轮是 4.0 倍，
> 差异全部来自本机噪声（同一配置 3 轮内波动可达 91k–169k）。
> 论文里应当报**区间**与**趋势方向**，并明确写出"1 ms 及以下效应落在噪声内"。
> 这也是为什么 §4.1 强调：这台机器的数字**只能看同轮内的相对关系**
> 与跨 RTT 的单调性，不能当绝对值。

### 5.2 可用性代价：`|Q1|` 变大有多脆

`-mode avail`：n=5，杀掉原 leader + k-1 个节点，7 次试验，看能否选出新 leader。

| 配置 | 杀掉 | 存活 | 成功率 |
|---|---|---|---|
| \|Q1\|=3 \|Q2\|=3 | 1 | 4 | **7/7 = 100%** |
| \|Q1\|=3 \|Q2\|=3 | 2 | 3 | **7/7 = 100%** |
| \|Q1\|=4 \|Q2\|=2 | 1 | 4 | **7/7 = 100%** |
| \|Q1\|=4 \|Q2\|=2 | 2 | 3 | **0/7 = 0%** |
| \|Q1\|=5 \|Q2\|=1 | 1 | 4 | **0/7 = 0%** |
| \|Q1\|=5 \|Q2\|=1 | 2 | 3 | **0/7 = 0%** |

结果是**阶跃**的，分界点严格等于「存活数 ≥ |Q1|」：
存活 < |Q1| 时不是"概率变低"，而是**必然**选不出 leader。
所以 `|Q2|=1` 配 `|Q1|=5` 的代价是：**任何一个副本挂掉，集群就失去选主能力**。

### 5.3 durability 代价：ack 的那一刻数据在几个副本上

`-mode lag`：串行提交（并发 1）、注入延迟 1ms、1500 个样本。
量的是 `Apply` 返回成功**那一瞬间**，日志里已有该记录的副本数
（用 `LastIndex()`，不是 FSM 的 `AppliedIndex()` —— 后者异步，会把 leader
自己都算漏）。

| 配置 | 副本数=1 | =2 | =3 | =4 | =5 | 均值 | **下界** |
|---|---|---|---|---|---|---|---|
| \|Q1\|=3 \|Q2\|=3 | 0% | 0% | 75.9% | 22.4% | 1.7% | 3.26 | **3** |
| \|Q1\|=4 \|Q2\|=2 | 0% | 77.5% | 20.0% | 2.3% | 0.1% | 2.25 | **2** |
| \|Q1\|=5 \|Q2\|=1 | **100%** | 0% | 0% | 0% | 0% | 1.00 | **1** |

**分布的下界严格等于 `|Q2|`** —— 这是 `|Q2|` 语义的直接实证。

**补充读数：复制落后量**（`runs[].replication_gap_entries`，窗口结束时
leader 日志末尾与最慢 follower 之差）：

| 注入延迟 | \|Q2\|=3 | \|Q2\|=2 | \|Q2\|=1 |
|---|---|---|---|
| 0 | 3,816 / 3,475 / 8,275 | 3,191 / 7,949 / 5,870 | 14,771 / 29,619 / **53,683** |
| 1 ms | 193 / 64 / 702 | 25 / 422 / 369 | 12,093 / 29,757 / **53,885** |
| 2 ms | 412 / 177 / 166 | 465 / 306 / 212 | 11,557 / 25,253 / **46,117** |
| 5 ms | 512 / 388 / 43 | 462 / 1,992 / 106 | 12,128 / 64,176 / **251,760** |

（三个数是 3 个测量窗口各自的落后量。`|Q2|` ≥ 多数时落后量始终在千条量级 ——
leader 每次提交都必须等够副本，日志末尾天然被压在一起；`|Q2|=1` 时 leader
完全不等人，于是可以一路领先，落后量随窗口**单调累积**。）

`|Q2|=1` 的含义因此非常清楚：**客户端收到"成功"时，这条数据 100% 只存在于
leader 一个副本上**，而且 leader 会越跑越前。

- 这不违反 FPaxos 安全性：`|Q1|=5` 保证没有原 leader 参与就选不出新 leader，
  已提交的日志不会被回滚，leader 崩溃重启后数据仍在。
- 但它意味着**介质丢失 = 已提交数据丢失**（FPaxos 的安全性论证覆盖的是
  崩溃-恢复，不是磁盘损坏）。
- 结合 §5.2：leader 一旦挂掉，集群会**一直不可用**直到它回来。

所以「`|Q2|` 变小换吞吐」这句话必须带上这两个注脚。
论文里如果把 `|Q2|=1` 当作推荐配置而不说这两点，是会被审稿人抓住的。

**中段才是可用的**：`|Q2|=2`（n=5）在 5ms 下仍有 46.0k ops/s（比多数 quorum
快 19%），同时 ack 时至少有 2 个副本有数据、能容忍 1 个节点挂掉。
这是 FAFT 真正想选的点 —— 而**选哪个点取决于故障域结构**，正是
`pkg/faft` 求解器在做的事。

### 5.4 规模维度（n=5/7/9，注入延迟 2ms）

| n | 多数 quorum | \|Q1\|=n, \|Q2\|=1 |
|---|---|---|
| 5 | 92,810（\|Q1\|=3,\|Q2\|=3） | 116,719 |
| 7 | 88,167（\|Q1\|=4,\|Q2\|=4） | 132,311（\|Q1\|=7） |
| 9 | 74,444（\|Q1\|=5,\|Q2\|=5） | 146,787（\|Q1\|=9） |

**多数 quorum 的吞吐几乎不随 n 变化**（93k → 88k → 74k）。
这不是反直觉的：等待是**并行**的，不是累加的 —— leader 向所有 follower
同时发 AppendEntries，提交等的是第 `|Q2|` 快的那个，所以 n 变大只增加
每条 RPC 里携带的条目数（实测 `append_entries_rpc_per_op` 从 0.18 降到 0.06），
不增加关键路径长度。

> ⚠️ **这一组只能看趋势，不能报绝对值**：所有节点跑在同一个进程、
> 同一个 Go 调度器、同一块 CPU 上。n=9 时测到的更多是调度器而不是协议。
> 单进程无法支撑 n > 9 的结论 —— 真实规模化需要多机，见 §7。

## 6. 复现命令

```powershell
# 环境（Windows：所有 go 命令必须带 -p 1）
powershell -File scripts\bootstrap-go.ps1

# 全部 raftbench 实验（实验 A/B/C），结果落 results/
powershell -ExecutionPolicy Bypass -File scripts\run-raftbench.ps1

# 单独跑一组
bin\raftbench.exe -mode bench -n 5 -q1 3 -q2 3 -delay 2ms `
    -ops 200000 -warmup 2000 -concurrency 512 -repeat 3 -duration 2s

# FAFT 的解析结果（ANALYSIS 级）
go run ./cmd/faftbench cost
go run ./cmd/faftbench domain
go run ./cmd/faftbench planners
go run ./cmd/faftbench evidence

# 端到端（MEASURED 级，但慢：本机 fsync ~5ms）
go run ./cmd/kvbench -spec 2x3 -duration 10s -warmup 3s -concurrency 32
```

### 模拟器校准状态（未通过，必须标注）

`pkg/sim/calib.go` 的拟合结果：`Calibrated=false, DivergencePoint=2`，
实测仅为模型上限的 **7.26%**（范围 4.44%–10.07%，2 个样本）。

含义：**模拟器只能用于趋势**，且必须在论文里写明它在 n=2 就已偏离。
不要用它报任何绝对值。样本数（2）也远不足以支撑外推。

## 7. 已知的、尚未测量的东西

诚实清单 —— 这些是论文里必须写成「future work」或「局限」的：

| 未测量 | 影响 |
|---|---|
| 真实多机、真实网络 RTT 与抖动 | 注入延迟是模型；真实网络的丢包/重排/拥塞未覆盖 |
| 真实磁盘 fsync 下的 quorum 效应 | in-memory 日志；真实部署里 fsync 可能与 quorum 等待重叠，把 `\|Q2\|` 的收益吃掉一部分 |
| n > 9 | 单进程下 n 再大测的是 Go 调度器而不是协议（`results/raftbench-n{5,7,9}-*.json` 已经能看出这个趋势） |
| 跨分片（Multi-Raft）下的 quorum 几何 | raftbench 是单分片；FAFT 的核心主张是分片间共享故障域，端到端部分只有 2 分片 |
