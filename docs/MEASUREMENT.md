# 测量方法、证据分级与本机限制

> 这份文档存在的唯一目的：让论文里的每一个数字都能被追问「它是怎么来的」，
> 并且答案是可复现的命令，而不是「我记得跑过」。
>
> 本项目曾经把解析计算写成「本项目实测」。那是错的，而且是很严重的一类错。
> 所以规则定死：**任何数字在写进论文之前，先在这里找到它的行**。

---

## 1. 四级证据

| 等级 | 含义 | 可以主张什么 | 不可以主张什么 |
|---|---|---|---|
| **MEASURED** | 真实系统跑出来的 | 本机、本配置下的绝对性能 | 其他硬件/网络/规模下的绝对性能 |
| **ANALYSIS** | 组合概率、闭式成本模型、约束求解 | 成本界、结构性质、可行性 | **任何性能声明** |
| **SIMULATED** | 离散事件模拟，且经实测校准 | 趋势 | 绝对值；校准未过时还须标注偏离规模点 |
| **DERIVED** | 本项目自行推导（非引用、非实测） | 作为推导结论 | 当作发现（若文献已有，须引用） |

代码里的对应物是 `pkg/faft/evidence.go` 的 `Evidence` 枚举与
`EvidenceManifest()`。清单可以直接跑出来核对：

```bash
go run ./cmd/faftbench evidence
```

**判据（写论文时逐条过）**：

1. 这个数字来自哪一级？
2. 这一级允许我写"我们测得"吗？不允许就改成"我们分析得出"。
3. 有没有把 ANALYSIS 的数放进性能表？—— 这是最容易犯的错。

## 2. 三套测量装置，各管一段

| 装置 | 产出 | 介质 | 能回答 | 不能回答 |
|---|---|---|---|---|
| `cmd/kvbench` | `results/{smoke-2x3,readheavy-after,writeheavy}.json` | 单机、BoltDB fsync、进程内 HTTP | 端到端读写延迟/吞吐；优化前后的相对改善 | 真实多机；大规模 |
| `cmd/raftbench` | `results/raftbench-*.json` | 单进程多 goroutine、in-memory 日志与传输 | **共识层**：quorum 几何对提交延迟/吞吐/消息数的影响 | 端到端吞吐；真实网络 |
| `pkg/sim` + `cmd/simbench` | `results/` 之外，随命令输出 | 离散事件 | 大规模下的趋势 | 绝对值（且校准未通过，见 §5） |

三者**不可互相替代**。特别是：

- `raftbench` 的数字**不是**「这个系统能跑多少 QPS」。
  它测的是共识协议本身，把路由、编解码、存储、fsync 全部剥掉了。
  它存在的意义是：把 `|Q1|`/`|Q2|` 这两个整数与吞吐/延迟的因果关系
  **单独隔离出来**，这在端到端基准里做不到（那些开销会把信号淹掉）。
- `pkg/faft` 的数字**不是**延迟也不是吞吐。它是概率与计数。

## 3. raftbench 的设计属性（为什么它的对照可信）

### 3.1 基线与实验组共用同一份代码

`third_party/flexiraft` 是 `hashicorp/raft@v1.6.1` 的改造版。在
`DataQuorumSize=0` 且 `ElectionQuorumSize=0` 时：

```
quorumSize()                  -> voters/2 + 1     （= 上游）
dataQuorumSize()              -> voters/2 + 1     （= 上游）
commitment.recalculate() 的 q  -> 回退到多数        （= 上游）
```

也就是与上游**逐行等价**。于是：

| 组 | DataQuorumSize | ElectionQuorumSize |
|---|---|---|
| majority（基线） | 0（= 多数） | 0（= 多数） |
| FlexiRaft | k+1 | 由 \|Q1\|+\|Q2\|>N 定 |

实现差异这个混淆变量被**彻底排除** —— 两组跑的是同一个二进制、
同一段提交逻辑，只差两个整数。

> 如果这里换成「上游 hashicorp/raft vs 某个独立实现的 FlexiRaft」，
> 任何差异都会被质疑「是不是实现质量问题」。这是本设计最重要的属性。

### 3.2 安全性条件在入口拦截

Flexible Paxos 要求 `|Q1| + |Q2| > N`（Howard et al., OPODIS 2016 §4.2）。
违反它**不会报错**，只会静默地丢已提交的日志。fork 内部只知道自己那一个
quorum，无法自检，所以 `buildCluster` 在建立集群前直接拒绝该组合。

### 3.3 一致性检查比的是状态指纹，不只是条数

跑完比每个节点的 `(applied 条数, lastIndex, hash)`。
`hash` 是 FSM 把每条命令的序号与 index 一起混进的状态指纹，
它能抓住「两个节点在同一 index 应用了不同命令」——只比条数抓不住。

这个检查在开发中**真的抓到过东西**：早先的 harness 复用 payload 缓冲区，
而 `InmemStore` 与 `InmemTransport` 传的都是引用，导致已提交的日志内容
被后续迭代改写。症状正是「条数与 lastIndex 完全一致、hash 不一致」。

### 3.4 in-memory 介质量不出 quorum 效应，所以要注入延迟

`InmemTransport` 的 RPC 是进程内 channel 传递，一次 AppendEntries 往返
只有几微秒。在这个介质上，「少等一个副本」几乎看不出差别 ——
不是机制不成立，而是**被测量的介质里没有等待**。

`cmd/raftbench/net.go` 在发送侧给每条 RPC 注入单程延迟：

- 延迟服从对数正态，**中位数**为配置值（用中位数而非均值，
  参数含义才不随 sigma 漂移）；
- pipeline 路径的语义是 `enqueue_i = max(t_i + d_i, enqueue_{i-1})`，
  即**按序交付但允许多个在途**（TCP 的模型），并用
  `maxInflightPerPeer` 做 BDP 上界与背压；
- 这是**注入**的延迟，不是实测网络延迟。所有结果都带
  `injected_delay_us` / `injected_jitter_sigma` 字段，论文里必须一起写。

> 这一条曾经写错过：早先的实现是「先等前一个 enqueue，再 sleep(d)」，
> 于是 `enqueue_i = enqueue_{i-1} + d_i` —— 延迟变成**累加**，每个 follower
> 的吞吐被钉死在 1/d，实测 p50 从 2ms 爆到 169ms，连心跳都排不上队，
> leader 反复因 lease 失效退位而不断重新选举。
> 症状是「延迟大得不像话 + term 一直涨」，很容易被误读成协议问题。

## 4. 本机限制（必须随结果一起读）

### 4.1 时钟地板 ≈ 300µs，且跳变可达 4.5ms

本机 Go 单调时钟是**粗粒度跳变**的。实测（`cmd/raftbench` 启动时自测，
写进结果的 `clock_floor_us`）：

| 测量 | 结果 |
|---|---|
| 200ms 忙等中的非零时钟跳变 | 142 次 |
| 跳变最小值 / p50 / p90 / 最大值 | 301.8µs / 992.1µs / 4.05ms / 4.52ms |
| `time.Sleep(10µs)` 最快返回 | 521µs |
| `time.Sleep(50µs)` 最快返回 | 440µs |
| `time.Sleep(500µs)` 最快返回 | 532µs |
| `time.Sleep(1ms)` 最快返回 | 1.03ms |
| 同一段 20e6 次忙循环的 10 次测量 | 8.98 – 16.56ms（±40%） |

**后果**：

1. **任何低于约 1ms 的延迟测量都会读成 0。**
   在 in-memory 介质（`-delay 0`）下逐次测延迟是无意义的 ——
   `raw_latency_ns` 全是 0 就是证据，不是 bug。
2. 结果里的 `latency_usable` 字段标记了这一轮延迟是否可信：
   判据是「注入延迟 ≥ 3× 时钟地板」。为 false 时，`notes` 里有一条
   显式警告。
3. 延迟不可信时，**主指标换成吞吐**：吞吐用跨秒窗口计算，
   时钟噪声会被平均掉。另外提供 `derived_avg_latency_ms`
   （Little 定律 `W = L/λ = 并发数 ÷ 吞吐`），它只用两个聚合量，
   同样不受时钟地板影响。
4. `client_saturation` = 客户端等待 Apply 的总时长 ÷ (并发 × 窗口)。
   **它接近 1 时吞吐才代表服务端容量**；否则吞吐只是「并发数 ÷ 延迟」，
   跨配置比较容量是不可靠的。

> 这条限制不是本项目能修的 —— 它来自运行环境（虚拟化时钟）。
> 能做的是**把它量出来、写进结果、在解读时避开**。
> 审稿人问「为什么 in-memory 的延迟是 0」，答案在这张表里。

### 4.2 单机、单进程

所有节点跑在同一进程里，共享同一个 Go 调度器与同一个物理 CPU。
所以：

- n 不能太大。n=9 以上测到的更多是**调度器**而不是协议。
- 没有真实的网络分区、没有跨机 RTT、没有共享交换机故障。
- 注入延迟是**模拟**网络，不是真实网络。

### 4.3 没有 `-race`

本机无 C 编译器（`-race` 需要 cgo）。所有并发代码的验证只有
逻辑推理 + 功能性并发测试。详见 [`ROADMAP.md`](ROADMAP.md) §三。

## 5. 实测结果（MEASURED 级）

以下全部来自 `results/raftbench-*.json`，由
`scripts/run-raftbench.ps1` 一键复现。
统一配置：n=5、payload 64B、512 并发、每轮 2s、**重复 5 轮取中位数**、
GC 阈值 400%（见 §5.5）、每条 RPC 注入单程延迟（对数正态，
中位数如表中所示，sigma=0.6）。

每一组的 `client_saturation` 都在 0.85–1.00，说明客户端一直压满，
吞吐代表的是**服务端容量**而不是"并发数 ÷ 延迟"。

### 5.1 收益侧：quorum 几何 × 网络 RTT

吞吐（ops/s，5 轮中位数，方括号是 5 轮的极值区间）：

| 注入单程延迟 | \|Q1\|=3 \|Q2\|=3（多数） | \|Q1\|=4 \|Q2\|=2 | \|Q1\|=5 \|Q2\|=1 | 极值比 |
|---|---|---|---|---|
| **0（纯内存介质）** | 191,621 `[147k–205k]` | 179,548 `[116k–196k]` | 197,715 `[175k–222k]` | 1.03 |
| **1 ms** | 147,653 `[120k–162k]` | 170,270 `[87k–180k]` | 184,765 `[170k–191k]` | 1.25 |
| **2 ms** | 93,260 `[67k–97k]` | 110,778 `[72k–115k]` | 188,438 `[184k–231k]` | 2.02 |
| **5 ms** | 41,186 `[41k–42k]` | 50,644 `[44k–51k]` | **166,747 `[72k–184k]`** | **4.05** |

p50 提交延迟（ms，5 轮最小值）：

| 注入单程延迟 | \|Q1\|=3 \|Q2\|=3 | \|Q1\|=4 \|Q2\|=2 | \|Q1\|=5 \|Q2\|=1 |
|---|---|---|---|
| 0 | 2.305 | 2.495 | 2.260 |
| 1 ms | 3.102 | 2.755 | 2.545 |
| 2 ms | 5.191 | 4.431 | 2.172 |
| 5 ms | 11.926 | 9.783 | **2.701** |

**读法**：

1. **延迟为 0 时三组没有区别**（三组区间互相重叠，中位数落在 180k–198k）。
   这是关键的**对照条件**：介质里没有等待，`|Q2|` 变小就没有收益。
   收益确实来自"不等副本"，不是实现差异或批次效应。
2. **多数 quorum 的吞吐随 RTT 近似反比下滑**：
   192k → 148k → 93k → 41k（0 → 1 → 2 → 5ms）。
3. **`|Q2|=1` 基本不随 RTT 变化**（198k / 185k / 188k / 167k）——
   提交路径上**完全不等 follower**，网络被移出了热路径。
4. **极值比随 RTT 单调上升**：1.03 → 1.25 → 2.02 → 4.05。
   这是本组实验最强的信号 —— 它是一条单调曲线，不是一个单点数字。
5. p50 的形状同理：多数 quorum 从 2.3ms 涨到 11.9ms（约 5 倍），
   `|Q2|=1` 全程稳在 2.2–2.7ms（≈ 注入延迟本身 + 时钟量化）。

> ⚠️ **不要报单点倍数**。同一配置不同轮次可差 30%（`|Q2|=1` 在 5ms 那组
> 5 轮区间是 72k–184k）。论文里应报**区间 + 单调趋势**，
> 并写明本机噪声量级。跨轮次（重跑整个 sweep）中位数还会再动 ±10%。

### 5.2 可用性代价：`|Q1|` 变大有多脆

`-mode avail`：n=5，杀掉原 leader + k-1 个节点，7 次试验，看能否选出新 leader。

| 配置 | 杀掉 | 存活 | 成功率 |
|---|---|---|---|
| \|Q1\|=3 \|Q2\|=3 | 1 | 4 | **7/7 = 100%** |
| \|Q1\|=3 \|Q2\|=3 | 2 | 3 | **7/7 = 100%** |
| \|Q1\|=4 \|Q2\|=2 | 1 | 4 | **7/7 = 100%** |
| \|Q1\|=4 \|Q2\|=2 | 2 | 3 | **0/7 = 0%** |
| \|Q1\|=5 \|Q2\|=1 | 1 | 4 | **0/7 = 0%** |
| \|Q1\|=5 \|Q2\|=1 | 2 | 3 | **0/7 = 0%** |

结果是**阶跃**的，分界点严格等于「存活数 ≥ |Q1|」：
存活 < |Q1| 时不是"概率变低"，而是**必然**选不出 leader。
所以 `|Q2|=1` 配 `|Q1|=5` 的代价是：**任何一个副本挂掉，集群就失去选主能力**。

`third_party/flexiraft/flexiquorum_test.go` 的
`TestElectionQuorumSizeIsEnforced` 把这条性质固化成了单元测试。

### 5.3 durability 代价：ack 的那一刻数据在几个副本上

`-mode lag`：串行提交（并发 1）、注入延迟 1ms、1500 个样本。
量的是 `Apply` 返回成功**那一瞬间**，日志里已有该记录的副本数
（用 `LastIndex()`，不是 FSM 的 `AppliedIndex()` —— 后者异步，会把 leader
自己都算漏）。

| 配置 | 副本数=1 | =2 | =3 | =4 | =5 | 均值 | **下界** |
|---|---|---|---|---|---|---|---|
| \|Q1\|=3 \|Q2\|=3 | 0% | 0% | 65.5% | 29.3% | 5.2% | 3.40 | **3** |
| \|Q1\|=4 \|Q2\|=2 | 0% | 69.1% | 25.7% | 4.9% | 0.3% | 2.36 | **2** |
| \|Q1\|=5 \|Q2\|=1 | **100%** | 0% | 0% | 0% | 0% | 1.00 | **1** |

**分布的下界严格等于 `|Q2|`** —— 这是 `|Q2|` 语义的直接实证。

**补充读数：复制落后量**（`runs[].replication_gap_entries`，窗口结束时
leader 日志末尾与最慢 follower 之差，5 轮取最大值）：

| 注入延迟 | \|Q2\|=3 | \|Q2\|=2 | \|Q2\|=1 |
|---|---|---|---|
| 0 | 3,232 | 17,505 | 43,387 |
| 1 ms | 476 | 679 | 34,105 |
| 2 ms | 512 | 576 | 48,382 |
| 5 ms | 511 | 1,119 | **95,545** |

`|Q2|` ≥ 多数时落后量始终在千条量级 —— leader 每次提交都必须等够副本，
日志末尾天然被压在一起；`|Q2|=1` 时 leader 完全不等人，落后量高两个数量级。

> ⚠️ **这条读数还藏着一个必须写进论文的限制**：落后量在
> `|Q2|=1` 下是**累积**的，不是有界的。原因很直白 ——
> 复制循环每次 `AppendEntries` 最多带 `MaxAppendEntries`（默认 64）条，
> 在 5ms 延迟下就是约 12.8k 条/秒；而 leader 在 167k ops/s 下产生日志的
> 速度快一个数量级。**超出的部分没有去处，只能在 leader 上堆积。**
> 跑几分钟就是 GB 级日志、恢复时间以分钟计。
>
> 也就是说：`|Q2|` 变小带来的吞吐收益，**只有在复制仍能跟上时才成立**。
> 跟不上的时候，系统不是在"更快"，是在"欠债"。这条约束是本组实验
> 最值得后续深挖的点（`MaxAppendEntries` × RTT × 目标速率的可行域）。

`|Q2|=1` 的含义因此非常清楚：**客户端收到"成功"时，这条数据 100% 只存在于
leader 一个副本上**，而且 leader 会越跑越前。

- 这不违反 FPaxos 安全性：`|Q1|=5` 保证没有原 leader 参与就选不出新 leader，
  已提交的日志不会被回滚，leader 崩溃重启后数据仍在。
- 但它意味着**介质丢失 = 已提交数据丢失**（FPaxos 的安全性论证覆盖的是
  崩溃-恢复，不是磁盘损坏）。
- 结合 §5.2：leader 一旦挂掉，集群会**一直不可用**直到它回来。

所以「`|Q2|` 变小换吞吐」这句话必须带上这两条注脚。
论文里如果把 `|Q2|=1` 当作推荐配置而不说这两点，是会被审稿人抓住的。

**中段才是可用的**：`|Q2|=2`（n=5）在 5ms 下仍有 50.6k ops/s（比多数 quorum
快 23%），同时 ack 时至少有 2 个副本有数据、能容忍 1 个节点挂掉，
落后量也只有千条量级。这是 FAFT 真正想选的点 —— 而**选哪个点取决于
故障域结构**，正是 `pkg/faft` 求解器在做的事。

### 5.4 规模维度（n=5/7/9，注入延迟 2ms，5 轮中位数）

| n | 多数 quorum | \|Q1\|=n, \|Q2\|=1 | 极值比 |
|---|---|---|---|
| 5 | 90,362（\|Q1\|=3,\|Q2\|=3） | 164,570（\|Q1\|=5） | 1.82 |
| 7 | 86,484（\|Q1\|=4,\|Q2\|=4） | 158,020（\|Q1\|=7） | 1.83 |
| 9 | 93,145（\|Q1\|=5,\|Q2\|=5） | 186,227（\|Q1\|=9） | 2.00 |

**多数 quorum 的吞吐几乎不随 n 变化**（90k → 86k → 93k）。
这不是反直觉的：等待是**并行**的，不是累加的 —— leader 向所有 follower
同时发 AppendEntries，提交等的是第 `|Q2|` 快的那个，所以 n 变大只增加
每条 RPC 里携带的条目数（`append_entries_rpc_per_op`：n=5 时 0.15，
n=9 时 0.06），不增加关键路径长度。

> ⚠️ **这一组只能看趋势，不能报绝对值**：所有节点跑在同一个进程、
> 同一个 Go 调度器、同一块 CPU 上。n=9 时测到的更多是调度器而不是协议。
> 单进程无法支撑 n > 9 的结论 —— 真实规模化需要多机，见 §7。

### 5.5 噪声控制：GC 阈值（`-gogc`）

`InmemStore` 在基准期间不截断日志（`SnapshotThreshold` 设到 4M），
一轮测量会在 leader 上留下几十万个**活跃** `Log` 对象。默认 `GOGC=100`
会让 GC 频繁扫描它们，把停顿打进吞吐 —— 这是本机除环境噪声之外的第二层噪声。

`cmd/raftbench` 默认把 GC 阈值提到 **400%**，并把生效值写进
`gc_percent`。这不是"调参调到好看"：它对**所有配置一视同仁**，
不偏向任何一组；它做的是把与自变量无关的方差压掉。

效果（同一台机器，`-repeat 3` → `-repeat 5` 且开 GC 调优）：

| 配置 | 调优前 3 轮 | 调优后 5 轮 |
|---|---|---|
| 5ms，\|Q2\|=3 | 38,506 `[37.6k–38.7k]` | 41,186 `[40.6k–42.0k]` |
| 5ms，\|Q2\|=2 | 45,956 `[45.2k–48.5k]` | 50,644 `[44.2k–51.1k]` |
| 5ms，\|Q2\|=1 | 154,437 `[90.9k–169k]` | 166,747 `[72.4k–184k]` |

区间宽度没有本质改善 —— 说明**剩下的噪声来自运行环境本身**
（§4.1 的时钟跳变与 ±40% 的忙循环波动），不是 GC。
所以本机数字的上限就是"报区间 + 看单调趋势"。

### 5.6 `|Q2|` 变小的**可行性条件**：`MaxAppendEntries`

§5.3 发现 `|Q2|=1` 时 leader 的复制落后量会无界累积。这一节把它从"警告"
变成**可操作的设计规则**。

控制手段是 `Config.MaxAppendEntries`（每条 `AppendEntries` 最多携带多少条
日志，上游默认 **64**）。直觉是：每次带得多，所需的 RPC 次数就少，
follower 就越容易跟上。

实验：n=5、`|Q2|=1`、`|Q1|=5`、注入延迟 5ms、512 并发、每轮 2s、4 轮。
落后量 = `runs[].replication_gap_entries`。

| MaxAppendEntries | 简单上限估计 `mae/delay` | 实测吞吐 | 4 轮窗口末落后量 | 形态 |
|---|---|---|---|---|
| **64**（上游默认） | 12,800 | 150,090 | 11,430 / 18,310 / 36,614 / 43,206 | **单调增长** |
| 128 | 25,600 | 166,462 | 4,444 / 2,448 / 36,169 / 28,041 | 不稳定 |
| **256** | 51,200 | 174,201 | 2,827 / 2,399 / 3,350 / 3,978 | **稳定有界** |
| 512 | 102,400 | 171,540 | 2,297 / 3,560 / 2,555 / 3,165 | 稳定有界 |
| 1024 | 204,800 | 166,383 | 2,750 / 2,275 / 2,478 / 3,283 | 稳定有界 |

**结论**：

1. **吞吐几乎不变**（150k–174k，落在噪声内）—— 也就是说
   把 `MaxAppendEntries` 从 64 提到 256 是**零成本**的。
2. **落后量差 10 倍以上**，而且形态完全不同：默认值下是**单调增长**
   （欠债越滚越大），提到 256 之后变成**稳定有界**（约 2.5k–4k 条）。
3. 转折点在 128 与 256 之间。

> **所以「`|Q2|` 变小换吞吐」的正确表述是**：
> 收益成立的前提是**复制仍能跟上**；而"能不能跟上"是一个**可调**的量 ——
> 把 `MaxAppendEntries` 提到目标速率所需的水位即可，代价为零。
> 这一条应当作为 FAFT 求解器的一条**约束**写进可行性判断：
> 选了小的 `|Q2|`，就必须同时选够 `MaxAppendEntries`（或接受受控的落后上界）。
>
> 上游默认 64 在这个速率下**不够** —— 这是一个真实的、可复现的部署陷阱。

**关于 `mae/delay` 这个简单模型**：它假设每个 RTT 只有一条 RPC 在途，
所以是**保守下界**。实测转折点（256，估计上限 51k）低于实测吞吐（174k），
说明实际有效在途深度约 3–4（受 `inmemPipeline` 的 `doneCh`/`inprogressCh`/
`consumerCh` 三个容量 16 的 channel 与串行 `decodeResponses` 限制）。
论文里不应把 `mae/delay` 当精确容量模型用；它的价值在于**指出控制变量**。

### 5.7 安全性实证：故障切换之后，已确认的写还在不在

这是整篇论文的底线问题，也是唯一一个"错了就全盘皆输"的实验。
FPaxos 用 `|Q1|+|Q2| > N` 从理论上保证已提交的日志不会被回滚
（Howard et al., OPODIS 2016 §4.2）；`-mode fail` 把它变成可复现的实测。

做法：持续施压并记录**每一条收到成功响应的序号** → 负载中途硬停 leader
（`Shutdown` + 关传输）→ 等新 leader（选不出就如实记录）→ 收尾后扫描
每个节点的日志做集合包含检查。

**判据必须分三层**（第一版实现把它们混在一起，得出了错误的"丢数据"结论）：

| 层 | 检的是什么 | 为什么必须单独看 |
|---|---|---|
| ① 无丢失 | 每条已确认的写至少存在于**一个**节点的日志里 | 真正的 durability |
| ② 无回滚 | **切换前**已确认的写都在**新 leader** 的日志里 | 选举限制是否真的起作用 |
| ③ 崩溃可恢复 | 被杀 leader 自己的日志含它确认过的**全部**写 | `\|Q2\|` 变小时最该盯的一条 |

> 第一版拿**全时段**的 acked 集合去查每个节点，于是被杀掉的 leader 必然
> "缺"了它死后才被确认的那些写 —— 那不是丢数据，是它已经死了。
> 这个错误会让任何方案都"不安全"，很有欺骗性。

实测（n=5，注入延迟 2ms，64 并发，施压 3s）：

| 配置 | victim | 已确认写 | 切换前 / 后 | ① 丢失 | ② 新 leader 缺 | ③ victim 缺 | 切换耗时 |
|---|---|---|---|---|---|---|---|
| \|Q1\|=3 \|Q2\|=3 | n1 | 85,608 | 45,053 / 40,555 | **0** | **0** | **0** | 144 ms |
| \|Q1\|=4 \|Q2\|=2 | n1 | 108,423 | 55,655 / 52,768 | **0** | **0** | **0** | 199 ms |
| \|Q1\|=5 \|Q2\|=1 | n3 | 337,523 | 337,184 / 339 | **0** | 不适用 | **0** | **8,004 ms（选不出）** |

**三层全部通过**：没有任何一条已确认的写丢失或被回滚。

**但 `|Q2|=1` 那一行暴露了它的真实风险面**：故障发生的那一刻，
337,184 条已确认的写**只存在于被杀的那一个节点上**（③ 验证它们确实都还在，
一条没少），而集群在 8 秒内**选不出新 leader**。那段时间：
集群不可用，且这 33 万条数据只有一份。每秒节点缺失数显示，
存活节点各缺 275 条 —— 那就是"寄存在死节点上、复制还没追上去"的部分。

> ⚠️ **这个实验不能证明安全性**。它做的是**证伪**：只要三层里任何一层
> 出问题，方案就是错的。论文里必须这样表述 —— 安全性靠 FPaxos 的理论论证，
> 实测是把"理论说不会出事"变成"在这些条件下确实没出事"。

### 5.8 多分片 + 整域故障：FAFT 核心主张的直接检验

前面所有模式都是**单分片**。但 FAFT 的核心主张不是性能，是这一句：

> 决定可达性的不是 quorum 的大小，而是它的**组织结构**。

这句话只有在「多分片 + 整域故障」下才检验得了 —— 一个域挂掉会同时影响
很多分片的副本。`-mode shards` 就是干这个的：400 个分片 × n 副本，
副本按 `(shard+i) % D` 摊到 D 个故障域上，然后杀掉若干整域。

**规模口径**：这是**多分片元数据面**，不是千卡集群。GPU 不参与共识；
真正压到元数据层的是分片数、故障域数与故障的相关性。

#### 结果（400 分片，每格一个独立进程，全部 `-hb 200ms`）

| n | 域数 D | 杀 | \|Q1\| | \|Q2\| | 存活副本分布 | 末刻可用 | 曾可用 | **算术界** | 退位瞬态 | 恢复期投票 |
|---|---|---|---|---|---|---|---|---|---|---|
| 3 | 5 | 1 | 2 | 2 | 2:240 3:160 | 100.0% | 100.0% | **100.0%** | 79.0% | 52/s |
| 3 | 5 | 1 | **3** | 1 | 2:240 3:160 | **40.0%** | 40.0% | **40.0%** | 81.5% | **1,711/s** |
| 3 | 5 | 2 | 2 | 2 | 1:160 2:160 3:80 | **60.0%** | 60.0% | **60.0%** | 52.5% | 1,082/s |
| 5 | 5 | 1 | 3 | 3 | 4:400 | 100.0% | 100.0% | **100.0%** | 82.8% | 135/s |
| 5 | 5 | 1 | 4 | 2 | 4:400 | 100.0% | 100.0% | **100.0%** | 80.5% | 167/s |
| 5 | 5 | 1 | **5** | 1 | 4:400 | **0.0%** | 0.0% | **0.0%** | 80.3% | **6,468/s** |

| 5 | 5 | 2 | **4** | 2 | 3:400 | **0.0%** | 0.0% | **0.0%** | 0.0% | **6,105/s** |

**10/10 精确等于算术界**：可用分片比例 = 「存活副本数 ≥ |Q1|」的分片比例。

#### 三条结论

**① 同一套 quorum 几何，在不同故障域结构下可用性完全不同。**

| 配置 | 域数 D=5 | 域数 D=3 |
|---|---|---|
| n=5, `\|Q1\|=3 \|Q2\|=3` | 100% | 100% |
| n=5, `\|Q1\|=4 \|Q2\|=2` | **100%** | **33.3%** |

`(4,2)` 这一档在 5 个域下毫发无伤，在 3 个域下掉到三分之一。
**这就是 FAFT 要解的那个问题** —— 几何能不能用，取决于副本怎么摊到域上，
而这两件事在文献里一直是分开处理的。

**② `|Q1| = n` 的代价不是"不可用"，是"持续抖动"。**
看最后三行：算术界是 0%，末刻可用也是 0%，但**恢复期投票率是 6,100–6,500 次/秒**，
是健康组的 **30–150 倍**（健康组 42–201/s）。

也就是说，存活副本数不够时，集群不是安静地挂着，而是
**上万个节点在无休止地拉票、失败、再拉票**。对运维的含义是：
CPU 不会降下来、日志会刷满、监控持续告警，而且它**永远好不了**
（除非副本数恢复）。这比"干脆不可用"更难处理 —— 而这一点是
统计 leader 数目的常规做法**看不见**的。

**③ 退位瞬态必须从"恢复"里剔出去。**
注入故障后**第一个采样**里，有 32%–83% 的分片仍然有 leader —— 那是没被杀到的
原 leader 在 `LeaderLeaseTimeout` 内还没退位。这是个**真实的短暂服务窗口**，
但绝不是恢复。

> 这个坑差点写进论文。第一版实现把瞬态算进"曾可用"，于是
> n=3/D=5/`|Q1|=3` 那一行报出 **80.5%** —— 而算术上只有 40% 的分片有
> ≥3 个存活副本，根本不可能。用算术反推验证：60% 的分片只剩 2 副本，
> 但其中 2/3 的原 leader 还活着，60% × 2/3 = 40%，加上真能选的 40%，
> 正好 80% —— 与实测分毫不差。n=5/D=5（存活 4/5）同理：
> 原 leader 存活概率 4/5 = 80%，实测 77.8%。
>
> **教训：可用性这类指标，"曾经可用过"和"稳定可用"必须分开报，
> 而且必须能用算术界交叉验证。对不上的时候，先怀疑测量，再怀疑结论。**

#### 实验纪律：本机规模上限（踩过的坑）

| 规模 | 单次耗时 | 稳定性 |
|---|---|---|
| 1000 分片 × 3 副本 = **3000** 实例 | 12–18 s | 连续多次稳定 |
| 1000 分片 × 5 副本 = **5000** 实例 | 40–60 s | ❌ **连续跑到第 7 次时把整台机器打到失去响应** |

出事时物理内存还剩 **22.8 GB**，所以不是内存问题：是大量 Raft 实例在整域
故障后同时进入选举风暴，16 个逻辑核全被打满、上万个定时器同时到期，
操作系统层面失去调度余量。

`cmd/raftbench` 现在把 `分片数 × 副本数 ≤ 3000` 做成**硬性拒绝**
（要突破得显式传 `-maxinstances`），并把这条实测依据写进了错误信息。
本节的矩阵全部用 **400 分片**跑（n=5 时 2000 实例），单次 14–16 秒。

> 比例是结构量，**400 分片与 1000 分片给出同一个数** —— 已在 n=3 上对照过
> （1000 分片：末刻 100%/40%/60%，400 分片：100%/40%/60%，完全一致）。
> 所以没必要为了"看起来更大"去冒死机的风险。

### 5.9 最优性：写消息数的可证下界（ANALYSIS 级）

> 证据等级：**ANALYSIS**。这一节里没有任何 wall-clock 数字 —— 它是对
> **可用性模型**的数学结论（"在给定故障模型下，任何放置 + 任何 quorum 选择
> 都不可能比这个更省"）。**等级低一级的含义**：如果模型本身错了，
> 求解器与下界会一起错；下界保证的是"求解器在模型内最优"，不是"模型正确"。

前面所有消融只能回答"A4 比分开优化更好"。审稿人的下一个问题必然是
**"那它是不是最优的？"** —— 没有下界，这个问题只能回答"我们试过的都更好"。

`pkg/faft/lowerbound.go` 给出 **relaxed lower bound**。要点：求下界要用可用性的
**上界**，所以每一步都必须是放宽，共四条（逐条写在源码顶部）：

① 两条路径分别取上界，不要求 Q1 与 Q2 **同时**存活（忽略耦合）；
② 忽略域容量与同域堆积；
③ 无事件项按最可靠域的单副本存活率算；
④ 事件项对成员数的**所有分拆**取可用性最大值（堆叠与摊开都在候选集里）。

守门测试（这三条是下界可信的全部理由，不是"顺便加的测试"）：

| 测试 | 断言 |
|---|---|
| `TestUpperBoundIsSound` | 90 个随机拓扑 × 2 组 K × 6 个随机放置 × 全部 q：**真实可用性 ≤ 上界**（含 D>12 与 K=D 两个分支） |
| `TestLowerBoundSoundAgainstBruteForce` | 对**放置 × 成员子集 × quorum 大小**三者一起穷举求真实最优，断言 **下界 ≤ 真实最优** |
| `TestUpperBoundMonotoneInEventSeverity` | 事件越严重（K 越大）上界越低（可证：φ 单调不增 + 逐点占优取期望） |

> 第一条测试第一次运行就抓到了 **BUG-28**：松弛 ④ 初版写成"成员尽可能摊开"，
> 而区域事件整域打掉时**堆叠更容易存活**（只需一个域不被命中）。方向写反的后果是
> 报出"我们的解低于理论最优"这种自相矛盾的数。详见 `BUGS.md` 第八节。

#### 结果（9 域 / 每分片 5 副本 / 目标 数据 0.999、控制 0.9999 / 48 个参数点）

```

其中有区分力的点（存在「可达但未达下界」的方法）：12 / 36

planner              可行点   达到下界   高于下界   未达可达目标   相对下界中位比
faft-joint           36      36        0          0            1.00×
majority             36       7       12         17            3.00×
tikv-pd              36       7       12         17            3.00×
orca                 36       7       12         17            3.00×
faft                 36      35        0          1            1.00×
faft-countselect     36      16        0         20            1.00×
flexiraft            36       0        0         36            —
flexiraft-dq2        36       0        0         36            —
```

三条读法，都要写进论文：

1. **联合求解在全部 36 个可行点上达到下界** ⇒ 在这些点上它的写消息数**可证最优**。
2. **只有 12 个点有区分力**。其余点上所有可行方法都已达到下界 ——
   那说明**下界不够紧**（松弛 ① 忽略 Q1/Q2 耦合是最主要的原因），
   不能读成"谁做都一样"。引用时必须同时给出 12/36。
3. **12 个下界不可行的点上，任何方法的不可行都不是方法缺陷**：
   连"最可靠域 + 最理想分拆"都达不到目标，目标本身不可达。

副本数扫描（skew=2.0，Q=1e-3，K=2）：

| n | 下界 \|Q2\| | 下界消息 | faft-joint | 比值 | majority | 比值 |
|---|---|---|---|---|---|---|
| 3 | 1 | 2 | 2 | 1.00× | 4 | 2.00× |
| 5 | 1 | 2 | 2 | 1.00× | 6 | 3.00× |
| 7 | 1 | 2 | 2 | 1.00× | 8 | 4.00× |
| 9 | 1 | 2 | 2 | 1.00× | 10 | 5.00× |
| 11 | 1 | 2 | 2 | 1.00× | 12 | 6.00× |
| 21 | 1 | 2 | 2 | 1.00× | 22 | 11.00× |

下界恒为 2（`|Q2| = 1`，即 Flexible Paxos 的结构性下限），随 n 增长不变；
多数 quorum 的消息数是 `n+1`。**注意这是消息数口径，不是延迟口径** ——
`|Q2| = 1` 的代价是 `|Q1| = n`（选举需要全部副本在线），
这个代价在 §5.2 与 §5.8 里是实测的。

**边界与诚实的说明**：

- `D ≤ 12` 时事件项按"命中全部 `C(D,k)` 组合"**精确求最大**；
  `D > 12` 时 `Topology.RegionalEventScenarios()` 改用轮转采样，
  与组合枚举不再等价，下界退回与命中集合无关的解析界
  `1 - H_min/D`（`H_min = ⌈(K·q - D·tol)/need⌉`）—— 此时**明显更松**。
  所以 n=1000 那种规模的下界弱于上表。
- 下界是**写消息数**的下界。差距为 0 = 消息数最优；差距 > 0 只表示"未证明最优"，
  不表示方案差。
- 复现：`bin\faftbench.exe lowerbound results\faftbench-lowerbound.json`

#### 运行成本：求解器的规模天花板（同一次排查的副产品）

生成上面那张表时暴露了一个问题：整条命令要跑 **12 分钟**。
按进程 CPU 一直在涨（不是死锁）判断是算不完，逐段计时后定位到
`SolveWithFailures` 的成员选择是 **O(n³·cost)** —— 它**对每个 k 都从空集重新贪心**。

| n | 单次联合求解（修前） | 单次联合求解（修后） |
|---|---|---|
| 5 | 78 ms | 131 ms（同量级，测量有负载噪声） |
| 9 | 274 ms | 1 787 ms |
| 11 | 973 ms | 5 200 ms |
| **21** | **561 193 ms（9.4 分钟）** | **70 436 ms** |

修法是嵌套贪心（贪心准则不依赖 k，逐 k 贪心的结果就是嵌套序列的前 k 项），
**严格等价**：用修前/修后两份结果 JSON 逐字段对照，离散字段差异 **0**。
整条命令 741 s → **52 s**。

> ⚠️ **这条直接约束论文能说什么**：n=21 单次联合求解仍要 70 s，
> 按此趋势 **n=1000 的联合求解不可行**。论文里 n=1000 的数字来自
> `AnalyzeScale` 的**解析外推**，不是联合求解器跑出来的 —— 两者必须分开表述。
> 详见 `BUGS.md` 的 BUG-31。

#### 顺带修掉的一处"不可复现"

`availabilityForKilledSet` 原来用 `for d, c := range perDomain` 做域卷积。
Go 的 map 遍历顺序随机，浮点加法不满足结合律，于是**同一个成员集合两次调用**
会给出最后几位不同的结果（实测 0.99977499514985479 vs …491）。
改成按域下标顺序卷积后，`TestMemberAvailabilityIsBitReproducible` 连打 200 次逐位相等。

**口径必须分清**：

| 结果类型 | 是否逐位可复现 |
|---|---|
| 解析结果（`pkg/faft`：可用性、消息数、下界） | ✅ **是**（修 BUG-32 之后） |

## 7. 已知的、尚未测量的东西

诚实清单 —— 这些是论文里必须写成「future work」或「局限」的：

| 未测量 | 影响 |
|---|---|
| 真实多机、真实网络 RTT 与抖动 | 注入延迟是模型；真实网络的丢包/重排/拥塞未覆盖 |
| 真实磁盘 fsync 下的 quorum 效应 | in-memory 日志；真实部署里 fsync 可能与 quorum 等待重叠，把 `\|Q2\|` 的收益吃掉一部分 |
| n > 9 | 单进程下 n 再大测的是 Go 调度器而不是协议（`results/raftbench-n{5,7,9}-*.json` 已经能看出这个趋势） |
| 跨分片（Multi-Raft）下的 quorum 几何 | raftbench 是单分片；FAFT 的核心主张是分片间共享故障域，端到端部分只有 2 分片 |
| 客户端视角的尾延迟在故障切换期间 | 只测了稳态窗口 |
| 分区（asymmetric partition）下的行为 | 注入的是延迟，不是分区 |
| `MaxAppendEntries` 转折点的**解析**模型 | §5.6 给出了实测转折点（128↔256）与控制变量，但精确容量模型还缺 —— `mae/delay` 是保守下界，实测有效在途深度约 3–4，这个数依赖具体实现（`inmemPipeline` 的三个 cap=16 channel），不能外推到其他实现 |
| 下界在 `D > 12` 时的紧度 | §5.9 的精确分拆只覆盖 `D ≤ 12`；`D > 12` 退回解析界，实测偏松（对 `q≤20`、`k≤3`、`D=1000` 时甚至退化为"忽略区域事件"）。所以"n=1000 也最优"这句话**目前没有**下界支撑 |
| 下界与真实故障数据的关系 | 下界是**模型内**的数学结论；模型参数（P、Q、K）目前来自敏感性扫描区间而非实测，见 `FAULT-DATA.md` |
